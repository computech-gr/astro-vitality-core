# MITOCHONDRIA v3 — durable medical advisor governance: implementation contract

## Scope and non-negotiable gates

This patch adds a WebCrypto SHA-256 evidence digest helper without changing the existing FNV session-only review flow. It does **not** implement durable sign-off or distributed rate limiting by itself. Those require server-verified data and database authorization, not browser assertions. Complete the following integration in Lovable, using the current repository schema, and do not report persistence as complete unless migration, RLS and end-to-end tests pass.

1. Create an append-only `medical_advisor_review_events` table through a reviewed Supabase migration. Each event: id, mission_id, crew_member_id, provenance, actor_user_id from auth.uid() (never client supplied), event_type (draft_created/returned/approved/revoked/superseded), revision, previous_event_id, evidence_sha256, canonical evidence reference or immutable snapshot, draft and final text, rationale, created_at, model and request metadata (no secrets). Store no real clinical data until explicitly enabled. Do not overwrite or delete history; revoke by a new event.
2. RLS: authenticated ground_medical active membership scoped to BOTH mission and crew, enforced for reads and writes. Server-controlled actor and event types. Avoid client-direct approval inserts; use authenticated RPC or server action with rechecked authorization. Restrict synthetic and real records from crossing. An existing ground_medical membership is not proof of medical licensure: label as reviewer acknowledgment, not certified clinical signature.
3. Before recording approval, server must independently reconstruct accepted observation evidence from an authoritative, integrity-verified source. Browser-only encrypted observations cannot be independently verified server-side. If no authoritative evidence exists, fail closed and keep session-only review; never persist a misleading 'verified' approval. Hash the server-reconstructed canonical evidence (UTF-8 SHA-256), compare to client hash, verify current evidence at read/print, reject stale approvals. Record immutable evidence snapshot/version and source record IDs. No silent fallbacks.
4. Rate limiting: enforce **atomic** per-user and per-mission quotas using database-backed or equivalent shared persistent storage, with 429 + Retry-After, not per-process memory. Reserve quota before provider call; bound payload size, concurrent requests, provider timeout and token budget. No raw patient content in logs. Distinguish 422 evidence-validation errors from 429 quota exhaustion.
5. AI generation: keep Responses JSON-schema output; validate every statement's exact evidence IDs and metric/value/unit/time against allowed evidence. Prompt-injection defense: treat observations as untrusted data. Limit retries (e.g. one server-side corrective attempt) without bypassing validator. No fabricated diagnoses, thresholds or treatment. Medical accuracy still requires independent human review.
6. Security: fail closed on missing credentials, auth/RLS, mission/crew mismatch, unverified synthetic provenance, missing server evidence, stale fingerprint, revoked reviewer or real-data policy. Keep `MITO_MEDICAL_AI_REAL_DATA_ENABLED` off. Explicit consent on every provider call. Do not claim `store:false` guarantees zero retention.
7. UI: clearly separate AI DRAFT, ADVISOR REVIEWED (research-only), REVOKED and STALE. Only show persisted status when verified by server. Show actor, timestamp, rationale, revision and evidence SHA-256; no legal digital-signature claim. Preserve local offline path.
8. Tests: unauthorized users, cross-mission/crew, stale evidence, revoked roles, concurrent approvals, RLS read/write, idempotency, synthetic/real isolation, tampering, rate-limit concurrency, 429, bad citations, responsive browser. Verify migration policy, full test suite, build, scientific gates and GitHub workflows for final commit.

## Release gate

Do not run a production migration or enable real-data processing without explicit owner approval. Prepare the migration and report it for approval. This is a governance foundation, NOT a production-ready medical-signature system.
