# P14 — Offline Mission Mode

P14 makes the local mission runtime useful when Earth/network connectivity is unavailable. It is intentionally designed so the cloud is not in the critical `sensor → astronaut` path.

## Implemented in P14

- AES-GCM encrypted local event persistence in IndexedDB.
- A non-extractable device-local browser key stored through IndexedDB structured cloning.
- Append-only semantics for mission-health events; conflicting reuse of an event identity fails closed.
- Local persistence API for observations, self-checks, readiness data, findings, actions, acknowledgements and operational events.
- Versioned P13 protocol cache with SHA-256 integrity metadata.
- Store-and-forward sync queue with idempotency keys and retry state.
- Conflict resolution by payload identity, source version, event timestamp and source priority; ambiguous ties require manual review.
- Transport abstraction for later secure Supabase/ground synchronization.
- Service worker that caches the public application shell/assets only. It does not cache health API responses.
- `/mission/offline` status surface showing encrypted-store, protocol-cache, connectivity, queue and conflict state.
- Live BLE observations and the P9 simple self-check are written into the encrypted local store and queued for later transport sync.
- P11 private readiness check-ins/results are written to the same encrypted local event boundary.

## Encryption boundary

P14 encrypts sensitive payloads before they enter the IndexedDB records store. The record wrapper retains only minimal operational metadata needed for append-only storage. The AES-GCM key is generated by Web Crypto as non-extractable and stored as a `CryptoKey` object in IndexedDB.

This is a practical browser-local encryption baseline, not a complete hardware-backed key-management claim. P16 threat modelling must review key access, session/crew authentication, device loss, key rotation and recovery.

## Sync semantics

P14 deliberately does **not** grant unauthenticated browser writes to a cloud health-data table merely to make synchronization appear complete. The sync engine exposes a transport contract; P15/P16 can bind that contract to a mission/crew-authorized Supabase service once the backend role/RLS/audit model exists.

The P14 reference transport is test-only and proves these semantics:

1. queue while transport/network is unavailable;
2. preserve the encrypted local record;
3. retry after reconnect;
4. use idempotency to avoid duplication;
5. resolve version/time/source conflicts deterministically;
6. fail closed to manual review when the tie cannot be resolved safely.

## Offline protocols and local intelligence

P12 and P13 are deterministic local modules. P14 caches the reviewed P13 protocol definitions, including authority and version. The cache does not invent clinical content and does not alter P13 safety rules.

## Service-worker safety

The service worker caches only same-origin public shell resources (`document`, `script`, `style`, `image`, `font`, `manifest`). Requests under `/api/` or containing Supabase identifiers are deliberately excluded to avoid leaking or replaying health responses through the Cache API.

## Exit evidence

The P14 automated tests verify encrypted-at-rest payloads, append-only behavior, disconnect/reconnect queue behavior, idempotent sync semantics, deterministic conflict resolution and protocol-cache integrity.

Production cloud persistence is **not** falsely claimed by P14; it requires the authorized backend boundary introduced with the ground/backend work.

## P15 authorized cloud transport

P15 binds the existing queue transport contract to an authenticated Supabase RPC. Local operation remains independent; failed or unauthorized remote sync leaves records queued locally. Mission membership and idempotency are enforced server-side.

## Recorded mission data and governed Supabase sync

The offline runtime is the local system of record while connectivity or authenticated mission access is unavailable. The `/mission/records` console decrypts records only inside the same browser origin and shows their source, metric/value summary, quality, timestamp and queue state.

When the browser has an authenticated Supabase session with an active mission membership, the existing P15/P16 `ingest_mission_event` RPC is used for idempotent store-and-forward synchronization. Anonymous writes remain denied. Cloud history is read only through the existing mission RLS boundary; local records remain available even if the remote transport is unavailable.

## Published cloud configuration state

The offline runtime must never remain indefinitely in a `CHECKING` state when the
published browser bundle does not have Supabase configuration. Missing
browser-safe Supabase configuration is surfaced as `CONFIGURATION REQUIRED`;
encrypted local capture, review, protocol cache, and queue semantics continue to
operate.

The published browser deployment requires `VITE_SUPABASE_URL` and
`VITE_SUPABASE_PUBLISHABLE_KEY`. Server-side helpers use the corresponding
`SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. Service-role credentials are never
placed in browser-visible variables.

The offline route uses the global site header only. It does not mount a second
page-local brand header.
