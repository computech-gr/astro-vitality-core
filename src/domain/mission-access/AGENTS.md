# Mission access rules

- P72 homepage role access: full mapped account emails live only in src/lib/p72-role-access.server.ts and reach the browser only through the public prefill server function on a role sign-in page (P72.5, owner-requested; never a password, session or token); signed-out homepage cards open that sign-in page, a demo session is asked before it is ended, a signed-in mapped account is routed to its console, and other accounts are never switched silently, because routing must never become identity transfer.
- P72.2 mission-level Ground Medical: an active Ground Medical membership without a crew binding is expanded in the identity loader to the crew of its own mission's caller-scoped roster RPC (pure helper mission-level-ground-medical.ts), because invitations cannot bind Ground Medical to crew while the database already authorizes mission-wide Ground Medical; only Ground Medical is expanded, originals are kept, and an unreadable roster adds nothing.
- P72.3 presentation target: role buttons preselect the owner-approved mission/crew in p72-role-access.ts only when the signed-in account already holds that exact membership (crew-scoped roles must match the crew; Researcher matches mission only and never inherits Ground Medical), and never fall back to another mission, because preselection is navigation, not authorization.
- P72.6 presentation sign-in (owner-requested, temporary for the presentation): the role sign-in page shows only fixed full masks for the email and password (no address letter reaches the browser); the real password lives in the server secret P72_PRESENTATION_PASSWORD and is used by a public server function that signs in only the role-mapped email and returns that session, off unless P72_PRESENTATION_SIGNIN_ENABLED is "true", because a password in page code could be read and reused by anyone.
- P72.6 global Researcher read: all-mission access comes only from the SQL-provisioned p726_global_research_readers grant via caller-scoped RPCs (owner-applied migration 0029; undo in supabase/pending), is synthetic-only and download/read-only, and is kept as a separate identity field (global-research-scope.ts), never a membership, so no Medical, attestation, correction, import, activation or operator check can see it.
