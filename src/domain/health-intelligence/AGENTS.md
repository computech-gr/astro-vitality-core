# Health intelligence rules

- P36 five-column lab candidates accept the existing pipe-delimited PDF geometry and explicit tab/multi-space tables only; digit-led scientific labels and decimal commas stay literal, collection dates never become observation instants, and catalog/human-review storage gates remain unchanged.

- Crew Self evidence (Companion and all four Health pages) is projected read-only by src/domain/health-intelligence/canonical-projection.ts from scalar envelopes, reviewer-accepted unified observations and catalog-validated domain entries; stored records are never rewritten, quality is never inferred, identical readings are charted once, and every in-scope record that cannot be charted is listed with a reason so evidence remains traceable.
- The Medical Report (/mission/health-report) is built deterministically by the pure read models in src/domain/health-intelligence (health-history-report.ts, unified-health-report.ts) for one authorized mission/crew/provenance: reviewer-accepted or human-verified rows only, never mixing real and synthetic, device rows only with declared provenance and canonical scalar metrics, everything else listed as excluded, and no diagnoses, thresholds or inferred trends.
- Unified medical intake stores observations only as versioned envelopes (legacy mitochondria.unified-observation.v1 instants; v2 explicit date/instant precision) through src/domain/health-intelligence/observation-store.ts: per-measurement catalog classification, reviewer-accepted rows only route to domain read models, and storage stays encrypted, append-only and offline (cloud copies only through the explicit v9.4 encrypted sync below).
- Medical Report PDF export captures print styles in an isolated clone in bounded page-aligned bands (never one full-height canvas, which exceeds browser canvas limits on long reports), cuts at report-item boundaries and generates local A4 bytes; fresh scope checks before and after rendering, and a failure is reported without invoking the separate Print action.
- Scientific Findings & Interpretation (scientific-findings.ts) is a pure read-only layer over the built Unified Health Report: first/last differences only for two distinct comparable time points at the recorded precision, cross-domain context only for signals listed verbatim in data/scientific/nikolas-cross-domain-context.v1.json, never causality, thresholds, diagnoses or fitness-for-duty; widening signal matching requires governed scientific review, not code-side synonyms.
- Structured intake formats (XLSX first sheet, plain JSON, FHIR R4 Observation/Bundle) are parsed on-device by universal-intake-adapters.ts into the same review candidates as CSV: explicit ISO calendar dates or zoned ISO timestamps (FHIR effective[x], never issued), no unit/date conversion, unmapped codes stay review-only, and repeated metric/time/value rows need explicit acknowledgment.
- Unknown Biomarker Review (unknown-biomarker-review.ts) groups review-only intake rows by normalized label + exact unit; decisions are ground-medical-only, append-only, persisted with pending requests in the encrypted local review ledger and always PENDING_NIKOLAS_REVIEW. Classification may only gain matches from data/scientific/catalog-extensions.v1.json entries that are APPROVED with a named reviewer, decision time and handbook evidence, alias an existing routed P36 metric with its exact unit, and do not conflict; the app never writes that registry. New biomarkers are recognized only through the P37 lifecycle (catalog-lifecycle.ts): scientific approval cites an independently provisioned source receipt, activation is role-based (any active Ground Medical member of the approval's mission, never the approver; staged in supabase/pending/20261108010000_p37_ground_medical_activation.sql over the installed 20261108000000 lifecycle, so roles come from existing memberships rather than email-specific grants) via caller-scoped RPCs, and devices match label+exact unit+specimen+method only from a verified signed snapshot (active-catalog-runtime.ts; trusted keys in data/scientific/catalog-signing-keys.v1.json; the server derives the Ed25519 key from the secret-store seed P37_CATALOG_SIGNING_KEY so the private key never leaves server memory), so activation needs no code change and never rewrites observations.
- The Scientific Health Summary (scientific-health-summary.ts) quotes biology only from the English handbook layers joined by exact catalog ID, counts only production Researcher-approved P40 interpretations as validated (synthetic demo approvals never count), and explains domain-overview vs Medical Intake count differences; screen, PDF and TXT share the same builder.
- Ground Medical evidence attestation (evidence-attestation.ts) is an optional second stage over already-accepted report rows: exact mission/crew/provenance ground_medical only, deterministic idempotent event IDs, revocation by superseding events, fingerprint-bound to the record version; it never changes catalog or scientific status.
- Review ledgers (attestations, unknown-biomarker requests/decisions) live in a separate encrypted local-only IndexedDB (infrastructure/offline/review-ledger-store.ts), never the mission record store, whose bounded reads they would otherwise displace, and are never queued for automatic sync (only the explicit v9 review sync reads them).
- Stored-observation review (stored-observation-review.ts) keeps lifecycle (Active/Erroneous/Superseded) separate from Ground Medical attestation; corrections are Ground Medical-only, validated first, then append the deterministic superseding record before the original's erroneous mark (retryable), and attestations reuse the report's fingerprints.
- Cloud review sync (review-sync.ts, src/lib/review-sync.functions.ts) is explicit, metadata-only and fails closed with "migration required" until the owner applies supabase/pending/20261101000000_v9_review_sync.sql; merges are append-only by event ID and never treat remote absence as deletion.
- Download PDF uses report-text-pdf.ts (searchable text from the same read models as screen/TXT, embedded Liberation Sans, never a DOM raster); Print stays separate. The PDF may only regroup or de-duplicate read-model text (attestation call-out on page 1, ranges of E-refs, ID+unit grouping, same-UTC-day spans never called longitudinal) and must never drop an evidence reference, audit event or review-status statement.
- Cross-device observation sync (observation-sync.ts, observation-sync-runner.ts, src/lib/observation-sync.functions.ts + .server.ts) is explicit and default-off: full canonical observation events are encrypted server-side (AES-256-GCM, HKDF per-scope keys from server-only secrets, keyed HMAC fingerprints) before reaching the pending v9.4 table, imports are append-only into the local store without joining any upload queue, and conflicts are reported, never overwritten; the combined action runs observations first and reviews second with independent results, and an attestation only shows Attested when the exact local record version is present.
- Unified Intake observations (sourceId "unified-intake") never use the legacy plaintext mission_events queue: runtime persistence skips enqueueing and the Supabase mission transport refuses older queued items before the RPC (held as needs_review); payload ceilings are measured in UTF-8 bytes so they always fit the staged ciphertext column.
- Researcher physiological interpretation (researcher-interpretation.ts) is one pure model shared by the four module pages, Medical Report screen, PDF and TXT: series per exact metric+unit (never converted), same-UTC-day never longitudinal, handbook context only via governedHandbookEntry exact ID within the same domain as a pending hypothesis, and cross-domain comparisons never performed while signals are missing, sparse, unaligned or measurement conditions are unrecorded.
- The P36 catalog reconciliation handoff (catalog-reconciliation-handoff.ts over data/scientific/p36-unknown-biomarker-reconciliation-handoff.v1.json) is display-only inside the Unknown Biomarker Review panel: it validates term IDs and PENDING_NIKOLAS_REVIEW status, fails closed on tampering, and never feeds classification, domain analytics, PDF/TXT, sync or the catalog-extensions registry; activation needs a separate governed patch.
- P36 Catalog Scientific Review (/mission/scientific-review, p36-scientific-review.ts) builds dossiers only from exact IDs in data/scientific/p36-scientific-review-crosswalk.v1.json, compares units by exact text, and records documentary SHA-256-chained worksheet entries in the local review ledger (catalog-level scope, never synced); its activation manifest always stays PENDING_NIKOLAS_REVIEW with zero ready terms, and data/scientific/p36-activation-manifest.v1.json must equal the builder output for an empty history.
- The P36 Scientific Decision Dossier (p36-decision-dossier.ts + -pdf.ts) is a read-only export over the review dossiers/manifest: every field carries an explicit basis (verified source statement vs proposed/conflict/missing/not validated), methods/protocols/units/approvals are never filled in, JSON carries a canonical SHA-256 content digest plus per-artifact digests verified by verifyDecisionDossier, and the PDF reuses the report-text-pdf layout engine without changing the Unified Health Report PDF.
- P36 final scientific authorization (p36-scientific-authorization.ts, src/lib/p36-scientific-authorization.functions.ts + .server.ts) lives only in the caller-scoped append-only cloud ledger staged in supabase/pending/20261104000000_p36_scientific_authorization.sql: Researcher-only final decisions, Ground Medical recommendations only, approvals must reference another account's matching recommendation, rows are re-verified (digest, per-term chain, rules, fingerprints) on every read and fail closed; local worksheet entries and exported dossiers never authorize, and activation still requires every gate plus the code-reviewed catalog-extensions registry.

- Calendar-date observations retain ISO text and datePrecision throughout intake, encrypted storage, correction, explicit ciphertext sync and reports; ordering/dedup use observation-date helpers, transport eventTimestamp uses recordedAt for dates, and mixed/repeated-same-date measurements never imply physiological first/last ordering. Source Unvalidated flags remain review-only and cannot be cleared by catalog matching.
- Report PDF adverse highlighting accepts only annotations validated by adverse-annotations.ts (approved versioned rule, exact metric/unit, included row, phase, baseline/provenance/context, quality) and always pairs red with a text marker; demonstration rules are synthetic-only, and the public sample PDF is regenerated by scripts/generate-synthetic-sample-report.ts through the same pipeline, so it never claims approval.
- Dynamic P36 handoff merges legacy dossiers with exact-scope local/cloud metadata through separate default-off authenticated RPCs behind a closed-by-default database admission row (app flags alone never admit writes); appends row-lock the authorizing membership/assignment, approvals must cite the source receipt's own validation reference, and the only migration order is docs/P36_AUTHORITATIVE_MIGRATION_SEQUENCE.md. Crew choices come from p36-crew-choices.ts (mission-level reviewers get the caller-readable roster), the pending-requests summary (p36-pending-requests-summary.ts) reads only submitter scopes and reports SYNCHRONIZED/FAILED only against an authorized cloud read, Researchers never see device-local registrations, and governed promotion exports never activate the catalog.
- The P37 synthetic demo catalog (synthetic-demo-catalog.ts + -runtime.ts + -sync.ts, src/lib/p37-synthetic-demo.*, installed from the 20261108020000 demo SQL) is a separate append-only demo: ledger, owner-only scope allow-list, "synthetic_demo" signing key derived with a domain label from the catalog secret. Its activated entries are the last classification stage in classifyWithGovernedExtensions (after handbook, governed extensions and production catalog; never replacing an exact match), only for synthetic rows of the same mission with label+exact unit, so they enter the normal intake/save/history/projection/report path; records carry metricId "demo:ubt-…" plus a validated catalogBasis (synthetic only, self-describing after revocation), sync re-checks them against the caller-scoped server demo snapshot, and devices auto-refresh verified snapshots when online. It never reads or writes production approvals, receipts or catalogs, so a demonstration can never become scientific approval.
- P38 bulk synthetic demo work reuses the P37 per-term demo functions through bounded (1–50) transactional batch wrappers staged in supabase/pending/20261108030000_p38_bulk_synthetic_demo.sql; the server derives deterministic idempotency keys per caller and exact request so retries never double-write, and the preflight (p38-bulk-demo-preflight.ts) proposes names/domains only from exact existing catalog IDs/names or, via source-section-classification.ts, from a SHA-256-cited source document listing the exact label+unit under a whole-heading versioned domain alias (committed value-free registries under data/source-evidence, regenerated by scripts/p39-source-section-evidence.ts); section proposals need explicit Researcher acceptance, cross-section/catalog disagreements stay manual, and a recognized conflicting section keeps later demo matches review-only, so ambiguous units, existing matches and duplicates never enter the owner scope (generated by scripts/p38-bulk-demo-scope.ts).
- P40 biomarker interpretations (biomarker-interpretation.ts) bind exact catalog ID + unit + domain (demo records also mission and synthetic provenance); the bundled registry is generated reproducibly from hash-pinned sources, handbook text stays a cited pending hypothesis, approval needs Researcher role, citations per claim, evidence basis and an exact acknowledgement, and no threshold language; device approvals are a hash-chained encrypted local ledger that fails closed when tampered with and reaches the shared registry only through an owner-merged approval package; screen, PDF and TXT render one verified snapshot and never change activation history or observations.
- P41 interpretation research extends P40 only: device APPROVE/REVOKE applies or merges solely with a server ATTEST (interpretation-attestation.ts, Ed25519 domain-separated from P37_CATALOG_SIGNING_KEY, signed in src/lib/interpretation-research.* only after a caller-scoped active Researcher membership read); literature (PubMed abstracts, public NASA NTRS, Crossref metadata) is queried with catalog concepts only, AI drafts keep only claims whose excerpts are verbatim in server-retrieved text (interpretation-evidence.ts), evidence/backlog attempts are append-only local ledger entries, and longitudinal-comparison.ts stays descriptive and neutral (no validated alert rules exist).
- P41.1 literature relevance (literature-relevance.ts) is deterministic and recomputed wherever references are used (panel, batch, server draft, editor conversion): bibliographic existence, scientific relevance and claim support stay separate; keyword hits, partial abbreviations and the spaceflight tag never establish relevance; nothing is pre-selected, only Relevant references enter automatic drafting, Potentially relevant ones need explicit Researcher selection, and with no usable reference the server reports insufficient relevant evidence without calling the AI.
- P42 document tables (document-table-reconstruction.ts) map header cells to column roles from an explicit vocabulary, never from a document template; every numbered source row becomes exactly one review row (gaps/duplicates reported, never filled), values keep their raw text and are normalized only when the document's own decimal convention proves it, units/timestamps are never inferred, sections reuse the frozen P39 heading rules, and OCR/token rows are always low-confidence. Review rules (document-intake-review.ts) keep identity conflicts held until Ground Medical resolves them (simulated-vs-real never), apply a stated examination time only on explicit reviewer choice, and exclude repeats/low-confidence rows from bulk selection.
- P54 biomarker health assessment (biomarker-health-assessment.ts) is the single read model for report screen, module series, PDF and TXT severity: RED/AMBER/NORMAL only from the verified-reference registry entry for the exact metric ID + unit + domain (or an already-validated approved adverse annotation), synthetic-demo references only for their own mission's synthetic data, never unit conversion or change-based judgement; everything else is NEUTRAL with a reason. The preliminary medical assessment (preliminary-medical-assessment.ts) is screen-only: de-identified packet, deterministic offline output, AI draft behind a default-off server flag for exact-scope Ground Medical + synthetic only, server-revalidated, and session-only clinician review; it never records a confirmed diagnosis.
- The Scientific Review page reaches the single P38 bulk Researcher UI through one anchored wrapper (p38-bulk-researcher-section) rendered by P37CatalogPanel before a mission is ready and by P38BulkDemoResearcher afterwards; the full interface shows only when the shared pure bulkResearcherVisibility rule finds Researcher capability and demo scope, so there is never a second bulk implementation or anchor.
- P55 bulk selection (p55-bulk-selection-engine.ts, p55-bulk-actions.ts) is one pure stable-ID engine shared by the Researcher P38 section, Global Scientific Review and Ground Medical activation: any record may be selected, hidden selections are counted in the preflight, and only records passing the existing per-action rules are sent through existing caller-scoped paths (triage RPC with deterministic server idempotency, P38 decision/activation batches); clarification notes and match acknowledgements have no governed write path and stay unrecorded, so selection can never widen authority.
- P56 Health Assessment (p56-health-assessment.ts) is the main report: one pure read model over the unified report, researcher interpretation and P54 assessment for the selected scope and date range, shared by screen, concise PDF (p56-health-report-pdf.ts through the shared text-PDF engine) and TXT. Related biomarkers are grouped only by exact catalog/demo ID through the validated pattern library (p56-pattern-library.ts over data/scientific/p56-health-pattern-library.v1.json, pending scientific review; doses rejected, each ID in one pattern); trends are earliest-to-latest at recorded precision, never same-day, never converted; colour/severity only from P54 verified references; automated AI notes attach only through validated packet refs. The full evidence report remains the optional technical appendix, and report-identity-redaction.ts removes the prohibited reviewer name from all rendered/exported report text without rewriting stored records. P56.1: every comparable series is profiled in full (p56-longitudinal-profile.ts: first/last/min/max, intermediate peaks/troughs, reversals, intervals; never interpolated), and review-triage flags come only from data/scientific/p56-review-priority-rules.v1.json (pending scientific review, fail-closed, dose-free); flags are a separate 'review' tone and never set RED/AMBER/NORMAL, so triage cannot masquerade as clinical classification. The main Download PDF is now the P58 professional report (below); the P56 concise PDF builder remains for its tests and the appendix path.
- P57 reference criteria (p57-reference-criteria.ts over data/scientific/p57-reference-criteria.v1.json) colour a result only when a Researcher approval of the criterion's exact fingerprint is server-attested (p57-criteria-attestation.ts, domain-separated Ed25519 key from the existing signing seed) for the report's mission with every mission-level condition attested, every per-observation condition recorded, no data-quality hold, the exact unit and agreeing criteria; decisions are hash-chained events in the encrypted local review ledger (p57-criteria-ledger.ts), applied through biomarkerAssessment options, and P54 verified references keep precedence. Candidates without an exact catalog identity can never be approved.
- P58 professional report (p58-professional-report.ts) is one model for screen, PDF (p58-professional-pdf.ts, adaptive with no page cap, vector charts, rows never split) and TXT: the Preliminary Clinical Assessment (p58-clinical-reasoning.ts over the governed data/scientific/p58-clinical-concern-library.v1.json) lists only supported concerns with supporting/contradicting evidence, criteria status (never "satisfied" before approval), missing tests and confirmation steps; optional AI elaboration (src/lib/clinical-reasoning.*, default-off P58_CLINICAL_REASONING_AI_ENABLED, synthetic + exact-scope Ground Medical) is re-validated and never changes status or priority; Ground Medical review is session-only with fingerprint-bound decisions and an audit trail separate from AI output.
- P59 premium PDF (p59-premium-model.ts / p59-premium-pdf.ts) is the default Download PDF with the P58 PDF kept as a separate export; literature-based demonstration colouring and the owner-directed synthetic identity mappings (data/scientific/p59-synthetic-demonstration-mappings.v1.json) run only on synthetic provenance for the exact mission and unit, never fill a row an approved P57 criterion classifies, and warning priority (p59-warning-priority.ts) stays a separate axis from clinical class that cannot reach high priority while a criterion's per-observation conditions are unrecorded.
- P60 cross-domain clinical patterns (p60-clinical-patterns.ts over data/scientific/p60-clinical-pattern-library.v1.json, owner-directed, pending Researcher review) run only when the P59 provisional literature demonstration is active (synthetic provenance): concepts bind by exact identity + unit, every threshold cites a listed source, statements are kept apart as observed / measurement quality / pattern / labelled hypotheses / missing context, every investigation is conditioned on Ground Medical, and pattern priority (rules PP-1..PP-5; high priority only from a NEWS2 3-point band, two converging independent findings, or a >10 mmol/L/24 h sodium change) never changes a result's clinical class; the library fails closed when an identity is ambiguous. The report loader reads every stored record count-based and reports coverage, and the methodology prints an order-independent observation census (p60-observation-census.ts) so an authenticated reviewer can compare exports with stored data.
- P60.1 premium-report terminology: each result carries one medical-review priority (its P60 pattern, else its uncovered P59 concern) that page 1, charts, assessments and the results table all print; P56 large-change flags render only as TREND REVIEW, observation-level data-quality rules as CHECK, and pattern-level data checks as a † marker on the series they name — so a change size, or a pattern check, can never read as HIGH PRIORITY or a measurement error, and classification stays a separate axis.
- P61 multi-date bulk import (p61-bulk-import.ts) assigns each row its own examination date (row date > date column > nearest preceding examination heading, sample-collection headings flagged, report/birth/print dates ignored) and never offers one document date across several; ambiguous, invalid, missing or conflicting dates stay unsaved until the reviewer picks a reading for that group. Bulk confirmation covers only rows that pass the existing save prerequisites and the source-aware duplicate key (same document + scope + metric + unit + date + value is never saved twice; other sources are possible duplicates needing individual review), and every save re-reads authorization and stored history before appending encrypted local events.
- Premium PDF pattern titles name a finding (fever, low vitamin D) only when its data are present, and chart date labels omit a label rather than overlap; date lines followed by no rows are shown as unapplied, so wording never asserts unimported evidence.
- P61.2 synthetic intake aliases (p612-synthetic-intake-aliases.ts over data/scientific/p612-synthetic-intake-aliases.v1.json) apply only after every exact catalog/handbook/governed/demo name match fails, only to synthetic rows of the register's mission, only onto an ACTIVE signed demo entry with byte-identical unit, name and domain, and never when the alias equals another active entry's name; the register stays PENDING_RESEARCHER_REVIEW, any defect disables it, and units are never converted or notation-normalized by the alias path. A CSV context/note column is kept verbatim as unverified provenance (candidate sourceContext, stored only inside the existing source excerpt), never as a clinical fact or new stored field.
- P60/P59 report wording derives timing, counts and fold changes from the recorded dates (no fixed "within one day"/"next day"/"two results"/"single measurement" text), names a value "raised" only when an applied criterion classifies it, and orders same-day items by biomarker identity and value (record IDs last) so PDF and CSV imports of the same data render identically; chart date labels never overlap (day numbers with the month once, then first/last/peak priority with omitted dates named in the caption) and data-check guide lines are listed below the axis, never labelled inside the plot.
- P61.3 unit notation (p613-unit-notation.ts) is a closed typographic rule list (UN-1 Celsius text, UN-2 caret powers of ten, UN-3 micro sign) tried only in synthetic demo recognition after exact-unit matching fails, never for production catalogs, aliases or real data; matched rows are stored under the catalog unit with the verbatim reportedUnit kept and validated, and scale or unit differences are never equivalent. The mapping decision register (p613-mapping-decision-register.ts) is display-only: it never changes classification, any approval claim or applied unresolved entry disables it, and unresolved names stay in the exception queue until the governed P36/P37 lifecycle decides them.
- P61.3 premium report: a result inheriting HIGH priority from a pattern without its own RED class prints the outlined "Associated with HIGH PRIORITY pattern" marker (never the red HIGH pill); every classified or prioritised series is charted beyond the default cap and any other series is named as not charted; page 1 lists every examination date and the running header prints the full crew name.
- P61.4 mapping governance (p614-mapping-governance.ts) adds no approval authority: Researcher decisions on the held P61.3 proposals are written only through the existing caller-scoped triage RPC (acceptance carries the structured mapping record) and the P37 synthetic demo decision, display names come from a closed per-proposal definition list, every requirement needs source-document or receipt evidence (unverified notes never count), Ground Medical activation stays separate, and held rows become eligible only when a verified signed snapshot recognizes the exact label + unit on re-import — never auto-saved, never for real data.
- P61.5 Researcher synthetic demo scope authorization and alias mappings go only through the caller-scoped pending RPCs in supabase/pending/20261112000000_p615_researcher_demo_scope.sql (existing scientific approver grant + global review basis; append-only grant/alias tables; aliases share the demo catalog sequence and are signed inside the demo snapshot); this keeps scope changes out of owner-run SQL while the database re-checks every rule.
- Observation sync server input schemas live in src/lib/observation-sync.schema.ts, stay strict and must accept exactly OBSERVATION_SYNC_ALLOWED_FIELDS (parity test); a missing envelope field there refuses whole batches and stripping it would silently alter records.
